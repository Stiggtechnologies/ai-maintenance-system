## Change and continuity

AppShell supplies a welcome slot; the established PresenceWelcome component delegates its canonical presentation to SyncAssistantWelcome without mounting its legacy runtime; its user/organization-keyed CopilotDock owns one Realtime hook and audio element. A personalized welcome is presentation data added as a transient user message under the existing session persona, with tools disabled for that greeting. No replacement response/system persona is introduced. Receive-only WebRTC requests no microphone. On audio playout completion, interruption, timeout or autoplay denial, browser resources are released. This is not quota-reservation settlement. Play allows a deliberate retry. Talk with Sync stops only an in-progress welcome, preserves an already authorized live conversation, and opens the same copilot, with its existing explicit Start conversation/microphone permission controls. Welcome mute controls are scoped to both tenant and user. Login, rerender, StrictMode and a new tab do not open a Realtime session; Play is required. A connecting/live session blocks duplicate starts, and welcome responses are capped at 1,024 output tokens without overriding the existing session persona.

Live chat and meeting modes share the controller; route/entity/mode changes update the existing Realtime context. Governed work answers use the existing authenticated conversation ID and canonical investigation stream/history. New/selected conversations end voice; text questions stop a welcome; dictation stops voice; closing the dock releases microphone. The greeting itself is transient and is not imported from or persisted into legacy presence history. Realtime general conversation is still transient; this PR does not add cross-device or all-surface general conversation persistence.

Authenticated profile identity must match the signed-in user before names/tenant identity are used. User/tenant changes remount the entire copilot, clearing history, attachments, permissions and voice state. Pending mic grants are stopped, pending negotiation is aborted/discarded, and old tool results cannot be sent into replacement sessions. Legacy unscoped cached plant/case context is not used in the new welcome. Scoped facts, actions and approvals still go through the server's existing tenant authentication, feature flags, quota reservation, evidence and confirmation paths.

## Release gates and rollback

Draft only. Architecture and privacy/tenancy review, PR CI, then authenticated staging browser/acoustic QA of receive-only SDP acceptance by the configured provider, autoplay replay, first/returning login, mic denial/interruption, live work-context handoff, logout and account/tenant changes remain required. Verify frontend/backend versions and existing tenant flags before release. The existing endpoint conservatively reserves 128,000 tokens per successful Realtime session. That local reservation is not provider billing. The per-organization advisory transaction lock serializes quota evaluation plus insertion; every concurrent request counts earlier open reservations. At the default 22M-token daily cap, 171 such allocations fit if no other usage exists; the 172nd does not. Each allocation also counts as one call. Provider negotiation failure/cancellation caught by the endpoint releases its open reservation. A successful handshake has no trusted server-side usage settlement or close callback here: browser End, successful welcome completion and disconnect do not release the row. It continues counting for the remainder of the UTC day; the row is retained and falls outside the next day's SUM. There is no successful-session TTL cleanup. This is a pre-existing fail-closed overcount, not evidence of 128K actual billed tokens. The reservation also does not enforce a total provider-session token ceiling over many responses.

OpenAI charges for actual response input/output tokens by modality; connections have no charge according to [Realtime cost documentation](https://developers.openai.com/api/docs/guides/voice-latency-cost?voice-api=realtime). Usage is supplied in response.done. The browser reports are not a trusted basis for reducing tenant quota, so this PR does not add a client-authorized release or settle API. Current [official pricing](https://developers.openai.com/api/docs/pricing) lists gpt-realtime-2.1 audio input $32/M, cached audio input $0.40/M, audio output $64/M, text input $4/M and output $24/M. The runtime environment can select another model; verify that configuration and rate before paid QA.

The first draft auto-created a fresh receive-only session on new-tab login. The revised draft deliberately defers audio to Play or Start conversation, eliminating that silent reservation/spend path while preserving the personalized visual welcome and unified voice. There is no login session to reuse. Existing live chat/meeting sessions are preserved by Talk with Sync; Play is disabled during one. Upgrading a completed receive-only welcome into a microphone session is not supported by this one-off SDP exchange; forcing a renegotiation or trusting client usage would require a separate design and review. Automatic audible first-login greeting is therefore a product decision, not enabled by this draft. Missing flags fail closed; enabling them or changing permissions, credentials, billing, privacy/network configuration or database policy requires the owner's approval. No such configuration or deployment change is included.

Frozen journey branch `agent/client-journey-integration` at `0a59d23b`, held branding PR659 and Context PR656 were inspected/referenced only and not merged or edited. No migrations, shared security guards, capability register or policy changes. Larger gaps remain: persistent general Realtime conversation continuity, Context inspector operating-picture release, and a product-wide authenticated acoustic qualification. Roll back this PR to restore the old AppShell welcome; no database rollback is needed.
