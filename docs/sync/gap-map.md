## 1. The resolved reuse-vs-rebuild decision: the Javis runtime is retired

The spec repeatedly instructs: reuse an authoritative existing JARVIS/Jarvis implementation rather than building a duplicate Sync beside it (§0 naming note, §51.3 rules 1–2, §73 requirement 3–4). That instruction has a definitive answer in this repository, decided and merged before this phase opened:

**PR #220 (`c69808a`, 2026-08-17) retired the Javis runtime — retire, not rewire — and the decision is final.** The inspection recorded in that commit found:

- All four Javis edge functions (`javis-orchestrator`, `javis-event-listener`, `javis-websocket`, `job-processor`) had **every query path broken against the live schema**: the nine `javis_*` tables they persist to (`context_cache`, `conversations`, `messages`, `pending_actions`, `event_queue`, `websocket_sessions`, `tool_definitions`, `tool_executions`, `conversation_state`) exist only in `supabase/_legacy_migrations/`, and the live tables they do reach (`work_orders`, `system_alerts`) were filtered by a `tenant_id` column neither table has — live tenancy is `organization_id`. Not one route in any of the four could serve one request.
- All four are now in `blockedLegacyFunctions` in `config/edge-function-boundary.json`, so the names cannot quietly re-enter the deploy allowlist.
- The four Javis UI components (`JavisBriefing`, `JavisDock`, `JavisDockInteractive`, `JavisPreferences`) were deleted with their runtime.

**Consequences for Sync, recorded so no later phase relitigates them:**

1. §51.3's compatibility rules ("do not mass rename", "feature-flag keys may remain `jarvis_*`", "do not strand existing tenant rollout state" §39) are **moot in the live system**: there are no deployed `jarvis_*` flags, tables, or routes to preserve. The one survivor is `user_preferences.javis_enabled` (`supabase/migrations/00000000000002_legacy_compat.sql:377`), a legacy-compat column read only by the never-imported `src/pages/OverviewDashboard.tsx` — it is not rollout state and gates nothing.
2. Sync therefore builds on **live conventions first-hand** — `organization_id` tenancy, `app_current_org()`, the current edge-function idioms — with `sync_*` names from the start (§11, §51.3 rule 4), and no compatibility layer.
3. The legacy Javis schema (`supabase/_legacy_migrations/20251025000000_create_javis_system.sql` and successors) is **reference material for §19's logical entities, never code to revive**. The deploy boundary enforces this.

This is the gap map's answer to §72 Step 3 ("identify the authoritative existing implementation for Sync and any legacy JARVIS implementation"): **there is none; the field is clear, and the clearing was a deliberate, merged engineering decision.**

## 3. Architecture-preservation contracts (§52–§76): what each requires of the schema later

The spec's build prompt (§73) splits every requirement into **build now** vs **preserve architecturally now**. This section is the preservation half: for each contract, what the schema and code conventions must keep possible, and which existing objects already carry part of the load. Nothing in this section is a Phase 0 build item.

**§51 — Brand/naming hierarchy.** Logical vocabulary only (Intelligence Core, Event Fabric, Action Fabric…). Requires of schema: nothing physical now; new objects use `sync_*` when created (§51.3 rule 4). The Javis half of §51.3 is resolved — see §1.

**§52 — Proactive and ambient intelligence.** The `SyncAttentionCandidate` contract (§52.4) will need a tenant-scoped store with `dedupe_key`, `expires_at`, evidence refs, and traceability to a source event (§52.5 "build now/preserve now" list). Existing partial carriers: `notifications` and `system_alerts` (both legacy-compat shims — a future migration must move this to live-tenancy tables). **Schema warning recorded now:** §52.4 forbids fabricated confidence percentages, and `decisions.confidence_score int default 80` (`00000000000001:262`) is exactly that — a default-valued confidence no model calibrated. Any future attention/decision surface must not inherit that column's semantics; a calibrated-source-or-null rule applies (§11.3 likewise).

**§53 — Autonomy ladder L0–L5.** The live `autonomy_level` enum is three-valued — `advisory | conditional | controlled` (`src/types/sir-contracts.ts:39`, mirrored on `autonomous_decisions`) — mapping onto L1/L3/L4. What §53.2's `effectiveAutonomy = min(...)` requires later: per-tool and per-capability maxima (nothing stores these today), tenant maxima (no live carrier; `tenant_settings.autonomy_default` is a legacy shim), and role ceilings — which **do** exist as `authority_limits` (`20260808210000_accountability_cascade.sql:90`: per-role `max_commitment_usd`, `max_risk_level`, `escalates_to_role`, with a mandatory `basis` string). Preserve: the min() composition must be computable server-side from governed rows; the model can never raise it (§53.2, §73 req. 9). L5 stays outside general autonomy per §53.3 — consistent with AGENTS.md invariant 6.

**§54 — Event fabric.** The `SyncEventEnvelope` (§54.3) requires, whenever event ingestion is built: tenant scope, preserved source identity/timestamps (`occurredAt` vs `observedAt`), idempotent ingestion, and a hard distinction between source events and AI interpretations (§54.4). Existing seams to extend: `sir_events`/`sir_queue`, `connector_runs` + `ingest_watermarks` (connector idempotency already practiced), Supabase Realtime. §54.5 names the reuse rule explicitly — no new event platform.

**§55 — World model / semantic layer.** §55.5: no graph database; map what relational schema already represents. Already present: `assets` → `components` → `damage_mechanisms` → `detection_techniques`; `job_plans.applies_to_mechanism_id` FK (`20260811090000_job_plans.sql:42`) — the strategy→task parent edge; class ontology (`asset_classes`, `asset_class_profiles`); twin naming (`asset_twin_templates/instances`). **Known hole the semantic layer cannot paper over** (_IA_ §4.7): there is no live asset hierarchy/functional-location structure — one text column on `component_life_events` (`20260830090000:49`) — so §55.2's Site→Area→System→Asset traversal has no data to traverse until that gap is closed as its own workstream. Preserve: stable entity IDs + `organization_id` scope on any new relationship table; relationship provenance columns (§55.3).

**§56 — Digital twin / operational state.** The `OperationalStateProvider` interface (§56.2) is an integration boundary, not a build item. Existing carriers: `sensors`, `condition_readings`, `operating_states`, `operating_mode_events`, twin tables. Preserve in any state-serving schema: source, timestamp, unit, quality metadata per measured value; derived vs predicted labelled as such; conflicting measurements visible, never silently averaged (§56.3).

**§57 — Simulation / what-if.** `scenarios` exists (`00000000000001:193`) but not in §57.2's shape (no assumptions/interventions/uncertainty structure). `model_register` + `model_predictions` + `model_input_snapshots` (`20260819090000_model_risk.sql`) already practice §57.3's honesty split for statistical models; `IntervalOptimization.tsx` computes a real Barlow–Proschan estimate (_IA_ §2 Group 3). Preserve: the deterministic/statistical/heuristic/speculation taxonomy (§57.3) as data, and never label a narrative guess a simulation.

**§58 — Multi-user / authority-aware collaboration.** Authority mapping exists: `decision_rights` (`00000000000024_decision_rights_matrix.sql`), `raci_assignments`, `authority_limits`. What §58.3 requires of a future meeting-outcome schema: dissent as first-class rows (agreed decision / unresolved disagreement / alternatives with cited evidence), never collapsed into consensus. §58.4: speaker attribution stays probabilistic data unless authenticated — no schema may treat diarization output as identity.

**§59 — Organizational memory.** The eight memory classes (§59.1) map onto existing stores: conversation (`cowork_messages`), operational history (`work_orders` et al.), outcome memory (`verification_obligations`, `learning_events`), organizational knowledge (`knowledge_contributions` + governance). The promotion rule (§59.2 — conversational claims do not become enterprise truth without deliberate capture) is **already enforced** for the knowledge base by the contribution/promotion machinery (`20260826090000_knowledge_contribution.sql`, `20260827140000_structural_promotion.sql`, human-gated) and by §23.6's example being repo policy (AGENTS.md invariant 10, draft-until-reviewed). Preserve: every future memory write path routes through an explicit promotion act with provenance; retention/deletion columns (§59.4) on any conversation store.

**§61 — Outcome verification and organizational learning (the other load-bearing contract).** The loop already has a spine, built and enforced: `recommendations` → (release blocked without a verification method by `check_recommendation_contract`) → `verification_obligations` (unique per recommendation; completed-needs-result CHECK; waived-needs-reason CHECK) → `learning_events` (`verification_obligations.learning_event_id` closes not-achieved results into learning) → `ca_verifications.strategy_updated_at/_by/_note` (`00000000000026_ca_effectiveness_loop.sql:34-36`) feeding execution back into strategy (_IA_ §1 edge E1). Cancellation propagation exists end-to-end in the Phase 0 transport (stream cancel → `onCancel` → abort upstream).

**§63 — Personality/communication.** Prompt-layer concern (§21's layered hierarchy); no schema. Preserve: mode/role adaptation as configuration, not forked assistants (§9 preamble).

**§64 — Attention, interruption, escalation.** §64.4 requires **auditable explicit acknowledgement** for critical notifications — no table today records acknowledgement; a future escalation store needs `acknowledged_by/at` and an escalation-state machine (§64.3). Must not be built on the legacy `notifications` shim.

**§65 — Offline/edge.** §65.5: do not build an edge platform now; do not assume permanent connectivity in session/action models. The idempotency-key convention (`sir-contracts`, FR-085) is the property that makes deferred sync (§65.4) possible later — every future Sync action write must carry one. `edge-node-manager` is a blocked legacy function, not a foundation.

**§66 — Multimodal perception.** Evidence discipline (§66.2): any future visual observation lands as an `EvidenceReference`-shaped record with source media, timestamp, model/version, uncertainty — the same shape Phase 0 typed. §66.3's safety rule (a vision model cannot satisfy a lockout checkpoint) belongs beside §71's boundaries when field mode is built.

**§67 — Cross-device continuity.** `SyncSessionHandoff` (§67.2) depends on a `contextSnapshotId` — i.e., §19.4's `sync_context_snapshots` logical entity. Preserve: when conversation persistence is designed (Phase 1 schema decision, §2 above), context snapshots get durable IDs so handoff is addressable later; permissions re-derive on the target device, never transfer (§67.3).

**§68 — AI evaluation and regression.** Versioned eval suites (§68.2) have partial carriers: `acceptance_tests` (`20260818090000_reliability_by_design.sql:186` — RAM acceptance, not AI evals), `research_runs`/`research_variants`. Requirement: eval sets become versioned artifacts with scoring rubrics (§68.3), gated on material prompt/model/retrieval changes (§68.4). No live schema for this; it is the largest genuinely-new preservation obligation after the ledger.

**§69 — Model registry, routing, shadow testing.** `model_register` exists (`20260819090000_model_risk.sql:38`) for engineering models — extending it versus a separate LLM registry is a naming-collision decision to make deliberately when §69.2 is built. The runtime half is already real: `llm-provider.ts` chain + `llm_provider_events` health. §69.4 shadow testing requires: mirrored inputs, **no shadow side effects** — enforceable only if every side effect goes through the tool layer (FR-080). §69.5 rollback = versioned config; feature flags (this branch) are the first carrier.

**§70 — Governance console.** §70.4: no console before controls exist, but every new capability exposes settings through a consistent layer. The `feature_flags` table created this branch **is that seam's first row-holder**; tenant capability policy (§70.2) extends it or sits beside it with the same `organization_id` + RLS shape.
