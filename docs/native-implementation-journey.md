# Native implementation journey — qualification draft

Issue #75 has a bounded post-purchase preparation slice inside the existing SyncAI deployment workspace. Azure activation offers **Continue implementation**; administrators can also enter from Deployments. No changes are made to the shared auth return, walkthrough, trust routes, decision-case contracts, connector adapters, evidence verification or MFA workstreams.

## Canonical contracts

`billing_subscriptions` remains the commercial authority. A journey references one same-company active subscription; Azure also requires its existing activated fulfillment binding and Microsoft's `Subscribed` state. Webhooks never call the journey or manufacture deployment success. Existing activation's verified Entra tenant and existing-administrator checks remain unchanged. A new company must use reviewed support-assisted provisioning before activation; this feature cannot create an organization, credentials, permissions or infrastructure.

`deployment_instances` holds additive implementation checkpoints, immutable company/purchase/outcome binding and revision. `audit_events` retains exact actor/command/payload receipts and before/after status. There is no new queue, job scheduler, import engine, evidence table or engineering approval model. Customer acknowledgement is a proposed later gate and remains unavailable pending canonical authority qualification.

Data mapping references existing assets, exact-asset evidence with a provisional legacy verifier stamp (not proof of immutable reviewed content), approved class-compatible `asset_twin_templates` and optional clean completed `connector_runs`. Authorized uploads, CMMS/historian reads, validation, retained rejects and document intake continue through their existing workspaces. No connection is configured or claimed by attaching a receipt. Unsupported systems and installation are human-assisted. This slice coordinates existing records and compilation; it does not automatically execute connectors or import files.

Preparation invokes `compile_asset_twin` and `run_asset_onboarding` with no billable AI pass. Existing matching twins are reused. Conflicting twins require engineering assistance, rather than being overwritten. A bounded transaction uses a coarse twin-table write lock because the existing compiler upserts and has no cooperating per-asset lock. This protects the check/compile race; throughput and contention require qualification before broad rollout. Template outputs stay drafts. The pilot `provision_deployment` starter factory is never called and cannot activate a customer journey. No synthetic assets or sensors are inserted.

Live prepare caps that global lock acquisition at **two seconds**, preserving any shorter caller lock budget. Success restores the caller setting immediately; an error restores it through the exception subtransaction and propagates without a receipt or revision change. The original request statement deadline remains unchanged; setting a statement timeout after the RPC begins is not an execution bound. There is **no server-side pilot/company allowlist**: deployment exposes preparation to every qualifying administrator with an active purchase, and the compiler-table lock serializes writers across companies.

The migration requires PostgreSQL **17** (repository configuration, production and native CI). Its **2-second lock, 30-second statement and 60-second transaction** limits are transaction-local. CLI **2.84.2** resets connection settings before each file, then batches that file and its migration-history insert in one implicit transaction. Manual/test application must likewise use `psql --single-transaction`. Failed application rolls back this file, not preceding Auth changes or earlier committed files. Timeout tests exercise the actual three limits, verify DDL/history rollback and lock release, and check successful commit restores settings in the same connection. No role defaults, pooled request defaults or shared production deployment controls change.

**First-result approval and implementation acceptance are unavailable.** Independent review found that canonical generic evidence can change after verification without clearing the original verifier stamp, and same-company users can forge stored asset approval fields. The command boundary refuses both completion actions; the panel explicitly identifies the human-assisted qualification step. Preparation treats mapping rows as provisional source references, not governed outcome proof. No verified-content or asset-approval authority is inferred from legacy mutable fields.

Required owning-rail changes before enabling completion: the existing authenticated verifier must issue a fingerprint/revision for the exact reviewed evidence content, and preserve that content or invalidate verification on edits; the canonical asset approval must provide an immutable authenticated act bound to exact asset/checklist revision. An implementation fingerprint taken later does not fix pre-capture provenance. Extending those shared rails requires ownership coordination and independent security/domain review; this branch does not change their permissions or production policy.

Source rows, descriptions, checklist values and connector payloads are not copied into company-readable deployment/audit checkpoints. Those checkpoints retain IDs and SHA-256 change fingerprints. Current evidence remains subject to its original authorized read path. The consumer compares the complete required catalog so deleted checklist rows cannot shrink the readiness denominator.

## Retry, interruption and correction

Commands lock the subscription/journey, check current membership and revision, and return an immutable receipt on an exact replay. Conflicting actor/payload/revision reuse is refused. Canonical billing event replay and ordering remain owned by the existing fulfillment/lifecycle rail.

The native panel retains an unresolved intent in session storage, scoped to actor and company. A transport failure is an unknown outcome; the panel reads canonical receipts before offering an explicit retry of that same intent. No automatic mutation retry runs. Signing out/context changes hides the old data and discards late responses. Browser session storage is not a cross-device durable draft; server checkpoints and audit receipts are durable, and another session can resume from the retained journey. Closed tabs may lose an unresolved browser intent; stale revisions and unique purchase binding still prevent a second committed journey.

Dry-run mapping/preparation validates sources without writes. Preparation catches an execution failure inside a subtransaction: its compilation/autofill changes roll back while the journey keeps a failure checkpoint. Fix the owning service's prerequisite, resume and explicitly retry. Pause retains customer imports, evidence and twin history. It does not delete imported data or attempt to reverse external actions. Resuming requires fresh review. Source/evidence changes invalidate the retained preparation manifest; historical receipts remain retained. Current acceptance is unavailable pending qualification. Corrections use the owning governed service and a new review, not receipt deletion or data truncation.

## Qualification and release boundaries

Synthetic PostgreSQL boundary tests execute command denial/replay/rollback and completion refusal against explicit doubles. A separate integration database applies the original baseline, compatibility, onboarding, governance, twin-library and Azure fulfillment migrations unchanged. It executes real compiler/autofill/human-input/readiness/approval functions, rollback at a real onboarding write, retry, tenant switch, dry-run conflict and direct same-company restricted-evidence reads. Its JWT shim and bounded later evidence/connector columns are a test substrate, **not** the full Supabase chain, GoTrue authentication, or signed-in browser qualification. A dedicated signed-in Playwright spec uses runner-provided existing demo fixtures on a fresh loopback Supabase stack: real human authentication and source verification, scope configuration, read-only dry run, preparation rollback at an injected database write, page reload, resume/retry, receipt reconciliation, duplicate start, tenant switch and non-admin denial. Credentials are neither embedded in that spec nor retained in browser traces. The PostgreSQL concurrency witness observes an actual competing compiler-table writer, finite acquisition failure, preservation of a stricter caller budget, outer statement cancellation with write rollback, setting restoration, and explicit same-intent retry without duplicate twins or receipts. Its hosted execution is a required qualification gate; listing/compiling the spec is not an execution pass. The repository's existing full migration-chain CI and billing regressions remain separate mandatory gates. No required gate is removed or weakened.

Before release: architecture and security/tenancy review of additive fields/RPCs; actual full migration-chain qualification; real-browser signed-in interruption and tenant switching; canonical provenance and immutable authenticated asset approval; supported connector operational evidence; customer-specific human approval/acceptance/training/support records; and separately authorized deployment. This PR is a draft and does not close #75's broader automated multi-source ingestion scope, certify live integrations or promote readiness registers.

Rollback before deployment is a code revert. After a separately approved database release, disable the panel/command grants and use reviewed forward corrections while retaining implementation and audit history. Never delete receipts, silently seed assets or weaken purchase binding. Release review must establish a recovery point and isolated restore witness: the observed daily production backups do not establish restore integrity/RTO, PITR is disabled and Storage object bytes are excluded. Auth configuration, Edge Function source/configuration and secrets require separate custodian-held recovery evidence.
