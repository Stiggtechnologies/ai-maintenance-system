# Sync Develop — Overlap Map (what already exists, and every canonical-home ruling)

_Created 2026-08-27. **Read this before building any register row.** This repository already
ships a large fraction of the Sync Develop specification. The last week of work here was
spent finding and demoting exactly the pattern a naive build of this spec would recreate —
two component-life stores, 39 orphaned Recovery RPCs, a register full of unreachable ✅s.
The owner's standing rule: search for existing implementations first; **extend, do not
parallel-track** (AGENTS.md invariants 1–3, 8; Lane split rule 1's mirror: the Feature lane
reuses, it does not duplicate)._

_Register: [register.md](register.md). Every claim below was verified against the working
tree on 2026-08-27 with control-checked greps (positive control: `fracas` = 45 files in
src+supabase). Verdicts: **REUSE** (the capability is this module, bind to it) · **EXTEND**
(the module is the canonical home; add columns/scope/write paths) · **CONFLICT** (the spec
as written would create a second implementation of something live — ruling given)._

    **RULING 23, AMENDED after review (2026-09-04).** Three things the first draft of this ruling did not carry, each found as a live contradiction rather than a style point:

    (a) **The work-order metrics read the ONE VERDICT as well as the ONE element predicate.** "Different denominator on purpose" is right and it is not sufficient: `sync_field_readiness_elements` is a WORK-ORDER predicate that knows nothing about the ten §28 package constraints, so a package with zero constraints recorded — `unassessed` on the one verdict — produced one payload with two NOT ASSESSED tiles and two 100% tiles about the SAME package, on the same screen. A metric may divide a different set; it may not apply a readiness standard the other three refuse to apply. The verdict is now read per job and mapped: `unassessed` excludes the job from both counts (as the index excludes it), `released`/`ready_for_human` do not hold it back, anything else does and carries the verdict's own sentence. `canRelease` is NOT the test — a released package reports `canRelease: false` because it is not released twice, and reading it as readiness would mark every released job in the product as blocked.

    (b) **A percentage's window is bounded at BOTH ends, and what falls outside is reported rather than dropped or folded in.** `required_by <= v_end` alone let work due 400 days ago define a denominator labelled "the next N days", and folding overdue packages into `not_projectable` disabled the I.28 forward figure permanently for any project that had ever slipped a date. Overdue draft packages are their own set with their own sentence.
