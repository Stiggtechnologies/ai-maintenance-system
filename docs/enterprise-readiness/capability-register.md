# Enterprise Operating System — Capability Register

_Program of record, created 2026-08-04. Direction from the product owner:
**every capability in the enterprise-OS specification must exist in the
application — nothing missed, nothing compressed.** This register enumerates
every atomic item of the specification with a stable ID. An item may only be
marked ✅ when the capability demonstrably exists in the application (working
code/data/UI, not documentation), with evidence linked. Status legend:
✅ exists · 🟡 partial foundation · ❌ absent. All ❌/🟡 items are open build
obligations._

_Companion analysis: [gap-analysis-enterprise-maintenance-os.md](gap-analysis-enterprise-maintenance-os.md).
Sequencing: the reconciled roadmap in that document §12. Register updates ship
with the PR that changes an item's status._

**2026-08-20 — 73 items demoted ✅ → 🟡, 72 of them by the reachability gate.**
The register tests asserted row count, unique IDs, tally arithmetic and a
no-silent-downgrade ratchet: five properties of the DOCUMENT, none of the
product. `src/test/capability-reachability.test.ts` now resolves each row's
cited symbols against the code and fails a ✅ whose citation has no non-test
caller, or whose cited table has no write path a customer can take. It caught
two shapes, and 3 rows show both:

- **read-only capability** (61 rows) — real schema, SELECT-only RLS, a demo
  seed and a read panel, with nothing in the application able to create a row.
  The tally moved ✅ 238 → 164 not because anything was removed but because
  "the screen renders" had been standing in for "a customer can do this";
- **unreachable logic** (14 rows) — a function or module written, granted and
  unit-tested with zero non-test callers.

**2026-08-20, second pass — 5 further demotions (✅ 170 → 164).** Hardening the
gate against a comment-as-caller, a getter vouching for a writer it does not
write, and an existence check standing in for reachability took C2.05, C3.12,
E1.01 and E12.01 out of ✅. C8.11 went with them for a different reason: it was
a bare ✅ with no evidence at all, over the one contract field that makes 7 of
17 cron-raised recommendations permanently un-approvable.

The remaining demotion is C8.18, which is not a reachability failure: the cron
producers deliberately leave `required_completion_date` blank rather than invent
a response interval, so those recommendations stay un-approvable by design.

Both figures were first published as "61 read-only / 7 unreachable". The 7 was
an undercount of the same kind this gate exists to catch: it was the number the
gate's FIRST version detected, not the number that was there. Hardening the
symbol judge — a comment no longer counts as a caller, and a getter no longer
vouches for a writer in the same migration — took it to 14 and moved three
further rows (C2.05, C3.12, E12.01) out of ✅. Two of those three had been
stating their own gap in prose while displaying a ✅.

The demotions are not a judgement on the work; the schema, the analytics and
the tests are all real and all still there. They are a correction to what the
glyph was promising. Restoring a ✅ now requires the write path or the caller,
and the gate re-checks it on every run.
